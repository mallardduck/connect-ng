# Codegen Architecture

## Design Philosophy

The codegen system is designed with a clear separation between **library-maintained code** and **product-generated code**. This allows products to use their own Kubernetes versions while sharing common business logic.

## What Gets Generated Where

### 1. Library-Maintained (Pre-Generated, Committed)

**Location**: `k8s/api/v1/zz_generated.deepcopy.go`

**What**: DeepCopy methods for shared embedded types:
- `ProductRegistrationSpec`
- `ProductRegistrationStatus`  
- `RegistrationRequest`
- `SystemActivationState`

**Why Pre-Generated**: These are version-independent struct definitions. Generating them once in the library means:
- ✅ Products don't need controller-gen for these shared types
- ✅ No version conflicts (these types don't change based on k8s version)
- ✅ Faster build times for products
- ✅ Smaller git diffs when embedding in products

**Maintenance**: Run `make generate` in `k8s/` after modifying types in `k8s/api/v1/`.

### 2. Product-Generated (Run-Time, Not Committed to Library)

**Location**: Product repo's `apis/<group>/v1/` directory

**What**: Our codegen produces minimal Go source files with kubebuilder markers:
```
apis/rancher.registration.suse.com/v1/
├── doc.go                          # Package doc + kubebuilder markers
└── productregistration_types.go   # ProductRegistration wrapper (embeds library Spec/Status)
```

These are **Go source files**, not generated code. They have kubebuilder markers that tell your codegen tooling (Wrangler, Kubebuilder, controller-gen) what to generate.

**What Products Must Generate**: After running our codegen, products run their tooling:

```bash
# Step 1: Our codegen generates the minimal Go source files above
go run ./cmd/generate-scc-types

# Step 2: Product's tooling generates everything else

# Option A: Wrangler (Rancher products)
go generate
# Produces: zz_generated.deepcopy.go, zz_generated_list.go, CRDs, etc.

# Option B: Kubebuilder / controller-gen
controller-gen object:headerFile=hack/boilerplate.go.txt paths=./apis/...
# Produces: zz_generated.deepcopy.go (DeepCopy + List types)

controller-gen crd:crdVersions=v1 paths=./apis/... output:crd:dir=config/crd/bases
# Produces: config/crd/bases/<group>_productregistrations.yaml
```

**Why Product-Generated**: 
- Each product may use different tooling (Wrangler vs Kubebuilder)
- Each product may use different Kubernetes versions
- List types, GroupVersion info, and DeepCopy output depend on the k8s.io/api version used
- CRD manifests must match the product's k8s version
- Keeps our codegen minimal and tool-agnostic

## Why This Design?

### Problem: Version Conflicts

If we pre-generated everything, products would inherit our k8s.io/api version:

```go
// BAD: If library pre-generates CRDs and DeepCopy for wrapper types
// Product is stuck with library's k8s version
require (
    github.com/SUSE/connect-ng/k8s v1.0.0   // Uses k8s.io/api v0.28.0
    k8s.io/api v0.30.0                       // CONFLICT! Product wants v0.30
)
```

### Solution: Version Independence

Our approach keeps the library version-neutral:

**Library Pre-Generates** (Version-Independent):
- DeepCopy for embedded types only
- These are plain structs with no k8s version dependencies

**Products Generate** (Version-Specific):
- DeepCopy for their wrapper types
- Using their own k8s.io/api version
- CRD manifests matching their k8s version

```go
// GOOD: Products choose their own k8s version
require (
    github.com/SUSE/connect-ng/k8s v1.0.0   // Version-neutral library
    k8s.io/api v0.30.0                       // Product's choice
)
```

## What About Shared Generated Code Safety?

The only shared generated code is `k8s/api/v1/zz_generated.deepcopy.go`, which is safe because:

1. **No k8s API references**: DeepCopy methods only reference the types themselves
2. **Stable across versions**: metav1.Time.DeepCopy() is the same in all k8s versions
3. **Struct-level only**: No runtime.Object or GVK manipulation

The product's wrapper types have their own DeepCopy methods that are generated with their k8s version.

## Summary

| Component | Generated By | Committed Where | Versioned By |
|-----------|-------------|-----------------|--------------|
| Shared Spec/Status structs | Hand-written | Library | Library |
| Shared DeepCopy methods | Library (make generate) | Library | None (version-independent) |
| Product wrapper struct | Library codegen | Product | Product |
| List types | Product tooling | Product | Product's k8s version |
| GroupVersion info | Product tooling | Product | Product's k8s version |
| Product DeepCopy methods | Product tooling | Product | Product's k8s version |
| CRD YAML manifests | Product tooling | Product | Product's k8s version |

This design allows the library to evolve independently while products maintain full control over their Kubernetes versions.
