# Design Rationale: Why We Don't Pre-Generate Everything

## TL;DR

**Question**: Why doesn't the library pre-generate DeepCopy methods and CRDs for product wrapper types?

**Answer**: Version independence. Products need to generate these using their own Kubernetes version, while the library's embedded types (Spec/Status) can be safely pre-generated since they're version-neutral.

## The Problem We're Solving

Products using this library want to use different Kubernetes versions:
- Rancher might use k8s.io/api v0.28.x
- NeuVector might use k8s.io/api v0.30.x  
- Future products might use k8s.io/api v0.36.x

If we pre-generated everything, products would be stuck with whatever k8s version the library used.

## What We Generate vs What Products Generate

### Library Pre-Generates (Safe to Share)

**File**: `k8s/api/v1/zz_generated.deepcopy.go`

```go
// Safe: Version-independent struct methods
func (in *ProductRegistrationSpec) DeepCopyInto(out *ProductRegistrationSpec) {
    *out = *in
    if in.RegistrationRequest != nil {
        in, out := &in.RegistrationRequest, &out.RegistrationRequest
        *out = new(RegistrationRequest)
        (*in).DeepCopyInto(*out)
    }
    // ... more pointer copying
}
```

**Why Safe?**
- No imports of k8s.io/api (except metav1, which is stable)
- Just struct field copying
- No runtime.Object interface methods
- No GVK manipulation

### Products Must Generate (Version-Specific)

**File**: Product's `apis/<group>/v1/zz_generated.deepcopy.go`

```go
// Version-specific: Uses product's k8s.io/apimachinery version
func (in *ProductRegistration) DeepCopyObject() runtime.Object {
    if c := in.DeepCopy(); c != nil {
        return c
    }
    return nil
}

// Calls library's pre-generated methods
func (in *ProductRegistration) DeepCopyInto(out *ProductRegistration) {
    *out = *in
    out.TypeMeta = in.TypeMeta
    in.ObjectMeta.DeepCopyInto(&out.ObjectMeta)
    in.Spec.DeepCopyInto(&out.Spec)         // <-- Library's method
    in.Status.DeepCopyInto(&out.Status)     // <-- Library's method
}
```

**Why Product-Generated?**
- Implements `runtime.Object` interface
- `runtime.Object` comes from k8s.io/apimachinery
- Different k8s versions may have different runtime.Object semantics
- Must match the product's chosen k8s version

## Example: Version Conflict Scenario

### ❌ If We Pre-Generated Everything

```go
// Library's go.mod
module github.com/SUSE/connect-ng/k8s
go 1.22

require (
    k8s.io/api v0.28.0
    k8s.io/apimachinery v0.28.0
)
```

```go
// Product's go.mod
module github.com/rancher/rancher
go 1.22

require (
    github.com/SUSE/connect-ng/k8s v1.0.0  // Transitively pulls v0.28.0
    k8s.io/api v0.30.0                      // CONFLICT!
    k8s.io/apimachinery v0.30.0             // CONFLICT!
)
```

Go modules would force the product to use v0.30.0 (higher version wins), but our pre-generated code was built against v0.28.0. This could cause:
- Subtle runtime bugs
- Type mismatches
- Incompatible API changes between versions

### ✅ Our Approach

```go
// Library's go.mod
module github.com/SUSE/connect-ng/k8s
go 1.22

require (
    // Only imports metav1 (stable across versions)
    k8s.io/apimachinery v0.28.0
)
// No k8s.io/api needed!
```

```go
// Product's go.mod
module github.com/rancher/rancher
go 1.22

require (
    github.com/SUSE/connect-ng/k8s v1.0.0  // Version-neutral
    k8s.io/api v0.30.0                      // Product's choice
    k8s.io/apimachinery v0.30.0             // Product's choice
    sigs.k8s.io/controller-runtime v0.18.0  // Product's choice
)
```

Products generate their wrapper DeepCopy using their own k8s version. ✨ No conflicts!

## The Architecture in Practice

### Step 1: Library Provides Go Source Templates

Our codegen outputs **Go source files** (not generated code):

```go
// Generated by our codegen from template
type ProductRegistration struct {
    metav1.TypeMeta   `json:",inline"`
    metav1.ObjectMeta `json:"metadata,omitempty"`
    
    // Embeds library's types (which have pre-generated DeepCopy)
    Spec   connectngv1.ProductRegistrationSpec   `json:"spec,omitempty"`
    Status connectngv1.ProductRegistrationStatus `json:"status,omitempty"`
}

// +kubebuilder:object:root=true  <-- Tells controller-gen to generate DeepCopy
```

### Step 2: Product Runs controller-gen

```bash
# Product runs this with their k8s version
controller-gen object paths=./apis/...
```

controller-gen generates version-specific DeepCopy:

```go
// Generated by controller-gen using product's k8s version
func (in *ProductRegistration) DeepCopyInto(out *ProductRegistration) {
    *out = *in
    out.TypeMeta = in.TypeMeta
    in.ObjectMeta.DeepCopyInto(&out.ObjectMeta)
    in.Spec.DeepCopyInto(&out.Spec)         // Calls library's pre-generated method
    in.Status.DeepCopyInto(&out.Status)     // Calls library's pre-generated method
}

func (in *ProductRegistration) DeepCopyObject() runtime.Object {
    // Uses product's runtime.Object from their k8s.io/apimachinery version
    if c := in.DeepCopy(); c != nil {
        return c
    }
    return nil
}
```

### Step 3: Everything Works Together

```
┌──────────────────────────────────────┐
│ Library (Version-Neutral)            │
│ - Spec/Status types                  │
│ - Pre-generated DeepCopy             │
│ - No k8s version dependencies        │
└──────────────┬───────────────────────┘
               │ Embedded by
               ▼
┌──────────────────────────────────────┐
│ Product (Version-Specific)           │
│ - Wrapper CRD type                   │
│ - Product-generated DeepCopy         │
│ - Uses product's k8s version         │
└──────────────────────────────────────┘
```

## What About CRD YAML Manifests?

CRD manifests **must** be generated by products because:

1. **Validation rules** depend on k8s API version
2. **CRD schema** evolves with k8s versions
3. **Conversion webhooks** are version-specific
4. Products may want custom validations/defaults

Example:

```bash
# Product generates CRDs with their k8s version
controller-gen crd:crdVersions=v1 paths=./apis/... output:crd:dir=config/crd/bases
```

## Summary Table

| Component | Pre-Generated? | Why? |
|-----------|---------------|------|
| Shared Spec/Status structs | ❌ Hand-written | Core business logic |
| Shared DeepCopy (Spec/Status) | ✅ Yes (library) | Version-independent struct copying |
| Wrapper CRD struct | ❌ Generated by codegen | Product-specific, but just Go source |
| Wrapper DeepCopy | ❌ Generated by product | Needs runtime.Object from product's k8s version |
| CRD YAML manifests | ❌ Generated by product | Validation/schema depends on k8s version |

## Benefits

✅ **Products choose their k8s version** - Not locked to library's version  
✅ **No version conflicts** - Library is version-neutral  
✅ **Faster product builds** - Shared types don't need regeneration  
✅ **Type safety** - Compile-time checking, not runtime  
✅ **Single source of truth** - ProductConfig drives everything  

## Trade-Offs

⚠️ **Two-step generation** - Products must run our codegen + controller-gen  
⚠️ **Documentation clarity** - Need to explain why two steps  
⚠️ **Boilerplate** - Each product needs hack/boilerplate.go.txt  

We believe the benefits far outweigh the trade-offs. The two-step process is standard practice in the Kubernetes ecosystem (kubebuilder, operator-sdk, etc.).
