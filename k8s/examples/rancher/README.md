# Rancher Example: Building Blocks Pattern

This example demonstrates the **building blocks** approach to integrating the SCC registration library.

Unlike the `simple` and `unified-config` examples (which use the `Setup()` convenience function), this example shows how to generate typed CRDs and manually configure the controller for full control.

## Overview

The library provides building blocks that ensure "all products have unified logic and interfaces" while giving products control over their implementation:

**Library provides (unified):**
- Reconciler with state machine logic
- OnlineHandler and OfflineHandler implementations
- SCC client abstraction
- Interface definitions
- Shared spec/status types

**Product controls (customizable):**
- Manager creation and options
- Scheme registration
- CRD generation and ownership
- Controller setup
- Product-specific configuration

## Building Blocks vs Setup()

This example uses the **building blocks** approach for full control. Compare with the `Setup()` convenience function:

### With Setup() (simple/unified-config examples)
```go
k8s.Setup(mgr, productconfig.ProductConfig{
    Product:   "rancher",
    Version:   "2.10.0",
    Namespace: "cattle-system",
    MetricsSecretName: "rancher-scc-metrics",
})
```

**Pros:** One line, quick integration, less boilerplate  
**Cons:** Uses unstructured CRDs, less control, no compile-time type checking

### With Building Blocks (this example)
```go
// Product controls scheme registration
utilruntime.Must(rancherv1.SchemeBuilder.AddToScheme(scheme))

// Product creates manager with custom options
mgr, _ := ctrl.NewManager(ctrl.GetConfigOrDie(), ctrl.Options{
    Scheme:           scheme,
    LeaderElection:   enableLeaderElection,
    LeaderElectionID: "rancher-registration.suse.com",
})

// Use Setup() to get both reconcilers
regReconciler, entrypointReconciler, _ := k8s.Setup(mgr, productconfig.ProductConfig{
    Product:   "rancher",
    Version:   version,
    Namespace: "cattle-system",
    MetricsSecretName: "rancher-scc-metrics",
})

// Product controls controller setup - uses typed CRD
ctrl.NewControllerManagedBy(mgr).
    For(&rancherv1.ProductRegistration{}).
    Complete(regReconciler)

// Register entrypoint secret controller
ctrl.NewControllerManagedBy(mgr).
    For(&corev1.Secret{}).
    Complete(entrypointReconciler)
```

**Pros:** Compile-time type safety, still simple, can add custom methods to CRD types  
**Cons:** Need to run code generator to get typed CRDs

**When to use which:**
- **Use Setup()** if: getting started quickly, unstructured is fine, minimal code
- **Use Building Blocks** if: need type safety, full control, large existing operator

## File Organization: Avoiding Chicken-and-Egg

To avoid circular dependencies during code generation, we separate pure configuration from generated types:

```
rancher/
  pkg/scc/
    config.go              # Pure data config (compiles standalone, NO imports of generated types)
    
  apis/rancher.registration.suse.com/v1/
    productregistration_types.go   # Generated - implements interfaces
    groupversion_info.go            # Generated - API group registration
    zz_generated.deepcopy.go        # Generated by controller-gen
    
  main.go                  # Imports BOTH pkg/scc AND generated types
```

**Key rule:** `pkg/scc/config.go` must compile WITHOUT generated types existing. It only imports the library's `productconfig` package.

This allows:
1. `pkg/scc/config.go` compiles standalone ✅
2. Generator creates types in `apis/` ✅  
3. `main.go` imports both `pkg/scc` and `apis/` ✅
4. No circular dependency!

## Integration Steps

### 1. Define Pure Product Config

Create `pkg/scc/config.go` with NO dependencies on generated types:

```go
package scc

import "github.com/SUSE/connect-ng/k8s/productconfig"

var Config = productconfig.ProductConfig{
    Product:   "rancher",
    Version:   "0.0.0-dev",  // Override at runtime
    Namespace: "cattle-system",
    MetricsSecretName: "rancher-scc-metrics",
}
```

This compiles standalone before any types are generated.

### 2. Generate Product-Specific CRD Types

This example includes a codegen program that uses the ProductConfig as a single source of truth:

```bash
go run ./cmd/generate-scc-types
```

See `cmd/generate-scc-types/main.go` for the implementation - it imports `pkg/scc.Config` and calls `codegen.Generate()`.

This creates:
- `productregistration_types.go` - CRD struct definitions (embeds library types)
- `groupversion_info.go` - API group registration  
- `doc.go` - Package documentation

The generated types automatically implement the library's interfaces by delegating to embedded types.

### 2. Generate DeepCopy and CRD Manifests

Use controller-gen to generate:
- DeepCopy methods (required by Kubernetes)
- CRD YAML manifests

```bash
# Generate DeepCopy methods
controller-gen object \
  paths=./pkg/apis/rancher.registration.suse.com/v1/...

# Generate CRD manifests
controller-gen crd:crdVersions=v1 \
  paths=./pkg/apis/rancher.registration.suse.com/v1/... \
  output:crd:dir=charts/rancher/crds
```

### 3. Initialize the Controllers

In your controller initialization code (main.go):

```go
import (
    rancherv1 "github.com/SUSE/connect-ng/k8s/examples/rancher/apis/rancher.registration.suse.com/v1"
    "github.com/SUSE/connect-ng/k8s/examples/rancher/pkg/scc"
    k8s "github.com/SUSE/connect-ng/k8s"
    corev1 "k8s.io/api/core/v1"
)

func main() {
    // ... create manager ...

    // Use pure config and override version at runtime
    productConfig := scc.Config
    productConfig.Version = version

    // Setup SCC registration - returns both reconcilers
    regReconciler, entrypointReconciler, err := k8s.Setup(
        mgr,
        productConfig,
        &rancherv1.ProductRegistration{},  // Typed prototype!
    )
    if err != nil {
        return err
    }

    // Register ProductRegistration controller using typed CRD
    ctrl.NewControllerManagedBy(mgr).
        For(&rancherv1.ProductRegistration{}).
        Complete(regReconciler)

    // Register entrypoint secret controller
    ctrl.NewControllerManagedBy(mgr).
        For(&corev1.Secret{}).
        Complete(entrypointReconciler)

    // Start lifecycle manager for jitter-based keepalive scheduling
    // This runs in a background goroutine and sets spec.syncNow when keepalive is needed
    ctx := ctrl.SetupSignalHandler()
    devMode := false  // or read from flag/env
    go k8s.StartLifecycleManager(ctx, mgr, productConfig, &rancherv1.ProductRegistration{}, devMode)

    // Start manager (blocks)
    mgr.Start(ctx)
}
```

**Key points:**
- Import `pkg/scc` for pure config (not `productconfig` directly)
- Import generated `rancherv1` types
- Override `Version` at runtime from flag/env/constant
- Start lifecycle manager in goroutine BEFORE `mgr.Start()`
- Lifecycle manager handles keepalive scheduling with jitter (20h ± 3h prod, 30m ± 10m dev)

### 4. Deploy the CRD

The library doesn't install CRDs - you choose the deployment method:

**Option A: Runtime installation** (Rancher's approach)
```go
import "sigs.k8s.io/controller-runtime/pkg/client"

// Install CRD at startup
crd := &apiextensionsv1.CustomResourceDefinition{}
yaml.Unmarshal(crdYAML, crd)
client.Create(ctx, crd)
```

**Option B: Static manifests** (RKE2, K3s approach)
```bash
# Include generated CRD in static manifest directory
cp charts/rancher/crds/rancher.registration.suse.com_productregistrations.yaml \
   /var/lib/rancher/rke2/server/manifests/
```

**Option C: Helm chart** (NeuVector approach)
```yaml
# In templates/crds/productregistration.yaml
{{ .Files.Get "crds/rancher.registration.suse.com_productregistrations.yaml" }}
```

### 5. Create Registration Resources

Users create secrets with registration data and a ProductRegistration CR:

```yaml
---
# Secret with registration code (user-created)
apiVersion: v1
kind: Secret
metadata:
  name: rancher-reg-code
  namespace: cattle-system
type: Opaque
stringData:
  registrationCode: "YOUR-SCC-REGISTRATION-CODE"

---
# ProductRegistration CR
apiVersion: rancher.registration.suse.com/v1
kind: ProductRegistration
metadata:
  name: rancher
spec:
  mode: "online"  # or "offline"
  registrationRequest:
    registrationCodeSecretRef:
      name: rancher-reg-code
      namespace: cattle-system
    # registrationAPIUrl: "https://scc.suse.com"  # optional
```

The controller will:
1. Read the registration code from the secret
2. Register with SCC (online) or generate request XML (offline)
3. Create a credentials secret with SCC login/password
4. Update status with system ID, activation state, etc.

## Interface-Based Design

The library works with **interfaces**, not concrete types:

```go
// Library defines interfaces
type ProductRegistrationObject interface {
    GetSpec() ProductRegistrationSpec
    GetStatus() ProductRegistrationStatus
}

// Generated types implement via delegation
func (pr *ProductRegistration) GetSpec() types.ProductRegistrationSpec {
    return &pr.Spec  // Delegate to embedded library type
}
```

This means:
- **Library never imports product types** - true decoupling
- **Products can extend** - add custom fields via embedding
- **Mode selection per-reconcile** - handler created based on spec.mode each time
- **Type-safe** - compiler enforces interface implementation

## What's Shared vs Generated

**Shared (from library `k8s/api/v1`):**
- `ProductRegistrationSpec` - common spec structure + interface implementation
- `ProductRegistrationStatus` - common status structure + interface implementation
- All getters/setters (30+ interface methods)
- Kubebuilder field markers (propagate to generated CRDs)

**Shared (from library internals):**
- Controller reconciliation logic (interface-based)
- Handler implementations (online/offline)
- Error handling and retry logic
- Unstructured adapter (works with any product's CRD)

**Generated (per-product):**
- Thin wrapper `ProductRegistration` struct that embeds library types
- API group name (rancher.registration.suse.com)
- GetSpec()/GetStatus() delegation methods
- Kubernetes registration with SchemeBuilder
- Kubebuilder type-level markers (CRD generation)
- DeepCopy methods (via controller-gen)

## Benefits

1. **Interface-based**: Library never imports product types
2. **Per-object mode selection**: Online/offline decided per-reconcile
3. **Product isolation**: Each product has own CRD, no conflicts
4. **Type safety**: Compiler enforces interface contracts
5. **Extensibility**: Products can add custom fields via embedding
6. **Based on scc-operator**: Proven patterns from real production code
